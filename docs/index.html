Your coding agent writes three.js.
Threesmith checks it.

three.js ships a release almost every month and removes old APIs. Agents learned it from years of old code, and they cannot see the canvas they draw on. Threesmith gives them the API of the three version you have installed, a review pinned to it, the assets and decoders the code needs, and the live scene in headless Chromium.

  1. Call three_fix (dry run), then three_fix write: true for the mechanical renames.
  2. Fix the asset paths (three_assets lists every reference and where it was looked for).
  3. Fix the 'shows nothing' group first, then confirm with three_check (screenshot) or three_inspect (why objects are not visible).

  5. Call three_review with only_new: true after each change, until no errors are left.
  6. Run three_check on the page (index.html) before you call it done.

Made for agents, not only for people

Everything an agent reads costs tokens and every wrong step costs a turn. Threesmith is built around that.

①Cheap by default

--tier cheap gives capped output and numbered steps small models follow; --tools core loads 14 of the 31 tools. Instructions only name tools that are loaded.

↻Fix loops that cost less

only_new shows new findings in full, seen ones as one line, and how many are fixed. code + file reviews code before it is saved.

≡One line per finding

file:line severity [rule] message Fix: …, the same in the CLI, MCP and hooks, plus structuredContent with a schema.

⟲Safe writes

Every write is one journal entry three_undo takes back. Protected folders, --read-only, dry runs first.

◉In Claude's loop

The plugin's hooks review each edited file and name broken asset paths right after the edit, explain three.js errors in command output, and brief the session at the start.

✦It learns, locally

100 lessons from real projects come back under the same error. A false alarm marked once stays hidden. Nothing leaves the machine.

It builds 3D models too, no Blender

60 ready-made kinds or your own JSON spec, as clean, deterministic .glb files with a node per part. Agents that cannot see pictures check them with three_model_view (front, side and top views as text) and three_model_lint. These are rendered by three.js itself, headless. All renders.

Honest limits

  • WebGL 2 in headless Chromium is reliable, also in CI. WebGPU is best effort.
  • Frame times come from software rendering: compare before and after. Draw calls and triangles are exact.
  • The review reads text, not types (three_types adds the type checker). It can be wrong; mark it with three_feedback.
  • No benchmark results are published yet; bench/ has the tasks and the grader.

FAQ

Does it need a GPU or a browser window?

No. Most tools read files. The browser tools use headless Chromium with software WebGL 2, which also runs in GitHub Actions.

Which three.js version does it check against?

The one in your node_modules/three. A rule knows the release that removed or renamed an API, so the same line is an error on a new release and a warning on an old one, and a rule whose replacement does not exist yet in your release stays quiet.

Does it work with React Three Fiber?

Yes: rules for useFrame (state set every frame, allocations), objects created in render and render priority, and rules R3F handles itself (dispose, colour space) are skipped.

Does it send my code anywhere?

No. There is no telemetry. Lessons and false-alarm feedback stay in ~/.threesmith, scrubbed of names, paths and code.

Is there one for Godot?

Yes: Godotwright is the same toolkit for Godot 4. Threesmith follows its design.
